## 2026-11-06 · BMP/TIFF/GIF/SVG 源元数据迁移与 XMP 扩展包重组（U01 第二段）

Type: requirement

按问题登记 U01 剩余项扩展迁移提取器（`src-tauri/src/migration.rs`），重编码副本继续保来源与色彩声明：TIFF 源把「文件头 + IFD0 + Exif/GPS 子 IFD + 越界值区」整块前缀逐字节迁入 eXIf（偏移不重排，仅定点修正方向/宽高、归零越界悬挂的 next-IFD 指针），另从 0x02BC/0x8773 取出 XMP 与 ICC；像素条带与前缀交错、结构损坏或 BigTIFF 布局时上报为「无法整块迁移」并要求明确确认，不把像素字节搬进副本、不当没有元数据。GIF 源重组 XMP 应用扩展块（跨 255 字节子块拼接，截断上报）；SVG 源提取完整 xpacket 区间；BMP 源迁移 V5 头内嵌（MBED）ICC，外链（LINK）逐项列出。JPEG 源新增 ExtendedXMP 支持：APP1/APP2 扩展分片按偏移拼回完整包并做 MD5 校验（32 字节大写十六进制 GUID，自含 RFC 1321 实现并以官方测试向量回归），摘要或覆盖不符上报为不完整 XMP，绝不静默取半截；存在扩展分片时 APP1 占位包不再被当作声明。

## 2026-11-02 · 安装包从 213MB 降到 6.3MB

Type: fix

用户反馈“安装包 200 多 MB”。拆开看：真正的程序 `chunjun.exe` 只有 18MB，多出来的 206MB 是 `bundle.windows.webviewInstallMode` 设成 `offlineInstaller` 后塞进 NSIS 的 `MicrosoftEdgeWebView2RuntimeInstallerX64.exe`——它本身就是压缩过的 cab，NSIS 再压也压不动，所以安装包体积等于两者相加。现在改成 `embedBootstrapper`：只内嵌约 2MB 的联网引导器，目标机器已经有 WebView2（Windows 11 自带，Windows 10 装了新版 Edge 也有）就跳过，缺失时才联网下载运行时。同时给 `Cargo.toml` 补 `[profile.release]`：`codegen-units = 1`、`lto = true`、`strip = true`，主程序 18MB → 16MB，安装包 213MB → 6.3MB。没有用 `opt-level = "s"`，图像编码是热路径，降优化级别会拖慢批量处理；也没有开 `panic = "abort"`，避免吞掉崩溃信息。代价是全新机器首次安装需要联网拉 WebView2 运行时，要交付纯离线包就把 `webviewInstallMode` 换回 `offlineInstaller`。

Tests: existing coverage: 这次只改打包配置与 `[profile.release]`，不涉及处理逻辑；`src-tauri/src/image_ops.rs`、`src-tauri/src/metadata.rs` 的既有测试不受影响，新产物已做启动冒烟验证（进程存活后关闭）。

## 2026-11-02 · 进度条按真实阶段推进，不再整张图才动一次

Type: fix

用户反馈“处理的进度条一直没有动”。用 WebView2 远程调试驱动真实界面复现：进度条只在某张图**整张处理完**时跳一格，第一张 1440×960 的图耗时约 2.7 秒（release 下 6.7 秒的 12MP 图更明显），这段时间一直停在 0%，观感就是卡死；单张导出更是从 0% 直接跳到结束。现在 `image_ops` 增加 `Stage` 回调（`process_with_stage`，原 `process` 退化为空回调的薄壳），在解码、应用参数、编码、量化调色板、映射颜色、压缩像素、校验结果、生成预览处上报 `(阶段名, 0..1)`；`export` 增加 `export_file_with_progress`，补上读取源文件、写入副本、回读校验三段；`run_job` 用 `Mutex<HashMap<index, f32>>` 记录每张图的阶段，按 `(已完成 + 各在途阶段之和) / 总数` 算出整体 `fraction`，随 `JobEvent` 下发并按 120ms 节流，前端进度页直接采用该值，文件名后显示当前阶段。

顺带修掉一个更隐蔽的卡顿：`preview_export`、`file_preview`、`export_preview`、`export_thumb` 原本是同步命令，Tauri 同步命令跑在主线程上，打开导出页时那次预览编码会把主线程占住约 2.7 秒，紧跟着的 `start_export` 只能排队，进度页因此在 0% 空转。四个命令改成 `async` 并 `spawn_blocking` 执行图像工作，主线程立即返回；实测预览仍在跑时点“开始导出”，首个阶段事件 250ms 内到达。

Tests: `src-tauri/src/image_ops.rs`（`stages_advance_monotonically_and_finish_near_complete`）、`src-tauri/src/export.rs`（`export_reports_read_write_and_verify_stages`）、`src/App.test.tsx`（阶段事件把进度条推到 42% 并显示阶段名）；`cargo test` 21 条、`vitest` 11 条通过。

## 2026-11-02 · 启动时按工作区适配窗口，修底部按钮被裁掉

Type: fix

用户反馈安装后启动窗口不是最大化，底部操作条看不见，手动放大后正常。根因是窗口按设计稿的 1440×960 **逻辑像素**创建：这台机器分辨率 2880×1920、系统缩放 200%，逻辑分辨率正好 1440×960，于是窗口物理高度 1920 等于整屏，而工作区只有 1856，底部 48 逻辑像素被任务栏吃掉，80px 的操作条只露出上半截。新增 `src-tauri/src/window_fit.rs`：`exceeds_work_area` 用物理像素比较窗口与 `monitor.work_area()`，放不下时先 `set_size` 钳进工作区、居中、再 `maximize()`——先钳后放大是为了点“还原”时回到钳制后的尺寸，否则会还原成溢出的 1440×960。窗口配置改为 `visible: false`，setup 里适配完再 `show()`，避免先闪一下原尺寸。前端补 `watchMaximized`：监听 resize 并回读 `isMaximized()`，标题栏按钮在“最大化/还原”之间切换图标与 aria-label，不再固定显示最大化图标。

实测（同一台 200% 缩放机器）：启动后 `innerHeight` 912 = `screen.availHeight` 912，`scrollHeight` 等于 `clientHeight`；导入 2 张图后操作条 `top 832 / bottom 912 / 高 80`，按钮全部在视口内；点“还原”后窗口仍是 1440×912，不重新溢出。

Tests: `src-tauri/src/window_fit.rs`（设计尺寸放得下不放大、200% 放大后需要放大、窄屏同样需要放大）、`src/platform/window.test.ts`（最大化状态跟随 resize 事件并能在取消订阅后停止）；`cargo test` 24 条、`vitest` 12 条通过。
